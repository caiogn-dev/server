## Bug corrigido — P3 · Logging de exceções

### OTP WhatsApp auth expõe str(exc) no campo `message` do log

**Arquivos:** `apps/core/auth/views.py:121,296` e `apps/core/auth/whatsapp_auth.py:274,339–347,390,407`

#### Problema

Mesmo padrão identificado em `cielo.py` (2026-10-01) reapareceu no fluxo OTP.

**`views.py`** — duas funções de view capturavam `WhatsAppAuthError` com:

```python
# ANTES (bug):
except WhatsAppAuthError as e:
    logger.error('[WHATSAPP AUTH API] Erro ao enviar código: %s', e)
```

O `%s % e` coloca `str(WhatsAppAuthError)` no campo **message** do log record —
chegando ao Sentry/CloudWatch como texto livre, sem scrubbing por campo.

**`whatsapp_auth.py`** — quando `send_template_message` falhava, um bloco
de debug capturava TODOS os atributos da exceção e os logava em 8 chamadas
`logger.error(f"...")` separadas, incluindo:

```python
# ANTES (bug):
error_traceback = traceback.format_exc()
logger.error(f"[WHATSAPP AUTH]   str(e): '{error_str}'")
logger.error(f"[WHATSAPP AUTH]   repr(e): '{error_repr}'")
logger.error(f"[WHATSAPP AUTH]   Traceback:\n{error_traceback}")
```

O traceback completo no campo `message` bypassa qualquer scrubbing configurado
no aggregator. Além disso, ao inicializar `MessageService`:

```python
logger.error(f"[WHATSAPP AUTH] Failed to initialize MessageService: {init_error}\n{traceback.format_exc()}")
```

E ao encerrar sem sucesso:
```python
logger.error(f"[WHATSAPP AUTH] All attempts failed. ..., last_error: {last_error}")
logger.error(f"[WHATSAPP AUTH] Final error message: {error_message}")
```

#### Correção

**`views.py`**: remove a variável `e` da chamada; a resposta HTTP já usa mensagem
genérica, então nenhuma informação de diagnóstico se perde.

```python
# DEPOIS:
except WhatsAppAuthError:
    logger.error('[WHATSAPP AUTH API] Erro ao enviar código')
```

**`whatsapp_auth.py`**: bloco de 8 `logger.error` substituído por único log
com tipo e código de erro (sem str/repr/traceback no message):

```python
# DEPOIS:
except Exception as e:
    error_type = type(e).__name__
    error_code = str(getattr(e, 'code', '') or '')
    logger.error('[WHATSAPP AUTH] Template %r falhou (%s, código: %s)',
                 template_data['name'], error_type, error_code or 'n/a')
```

Para o init do `MessageService`:
```python
# DEPOIS:
except Exception as init_error:
    logger.error('[WHATSAPP AUTH] Falha ao inicializar MessageService (%s)',
                 type(init_error).__name__)
    raise WhatsAppAuthError('Falha ao inicializar serviço de mensagens') from init_error
```

O `raise ... from init_error` preserva a cadeia completa no `__cause__` (visível
em Sentry como cadeia de causa), sem jogar `str(exc)` no campo message.

## Bug corrigido: `llm_error` expunha `str(exc)` com possível API key [P1]

**Tipo:** P1 — vazamento de credencial em resposta HTTP autenticada.

### Causa raiz

**Arquivo:** `apps/stores/services/ai_insights.py`

Três pontos onde `str(exc)` chegava ao cliente via campo `llm_error`:

```python
# ANTES (_resumir_erro, linha 132):
return f'{nome}: {str(exc)[:120]}'

# ANTES (generate_daily_summary, linha 604):
except Exception as exc:
    erro = str(exc) or type(exc).__name__
    logger.error('[ai_insights] resumo diário sem IA (loja=%s): %s', ..., erro)
    # ...
    'llm_error': erro if source != 'llm' else None,

# ANTES (generate_conversation_insights, linha 683):
except Exception as exc:
    erro = str(exc) or type(exc).__name__
    logger.error('[ai_insights] análise de conversas sem IA (loja=%s): %s', ..., erro)
    return {..., 'llm_error': erro, ...}
```

Exceções de clientes LLM (OpenAI, Anthropic, NVIDIA NIM) frequentemente incluem a
chave de API no texto da mensagem de erro:

```
RuntimeError: Authentication failed with key sk-nvidia-SECRETAPIKEY1234567890abcdef
```

Isso chegava ao dono de loja autenticado em texto puro:

```json
{"source": "template", "llm_error": "RuntimeError: Authentication failed with key sk-nvidia-SECRET..."}
```

O mesmo padrão `logger.error(msg, ..., erro)` colocava `str(exc)` no campo
`message` do log record — campo que não pode ser filtrado por campo no
Sentry/GlitchTip (o scrubbing por campo só funciona em `exc_info`).

### Correção

```python
# DEPOIS (_resumir_erro):
def _resumir_erro(exc: Exception) -> str:
    nome = type(exc).__name__
    if 'timeout' in nome.lower():
        return 'timeout'
    return nome  # sem str(exc)

# DEPOIS (generate_daily_summary e generate_conversation_insights):
except Exception as exc:
    erro = type(exc).__name__           # só "RuntimeError", sem detalhes
    logger.exception('...')            # traceback em exc_info — redatável
    # ...
    'llm_error': erro,                 # "RuntimeError"
```

- `_resumir_erro`: verificação de timeout agora só olha o nome da classe (não
  `str(exc)`), removendo o único caminho que lia a mensagem.
- `logger.exception` coloca o traceback completo em `exc_info` (campo separado,
  sujeito a redação por Sentry/GlitchTip); nenhuma string da exceção vai para
  o campo `message`.
