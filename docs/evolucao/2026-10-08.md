## Bug corrigido — P3 · Logging de exceções

### CampaignViewSet actions colocam `str(exc)` + traceback completo no campo `message` do log

**Arquivo:** `apps/campaigns/api/views.py:675,696,714,732`

#### Problema

Exatamente o mesmo padrão removido de `apps/core/auth/whatsapp_auth.py` pelo PR #387
reapareceu em `apps/campaigns/api/views.py` nas quatro actions de ciclo de vida de campanha:

```python
# ANTES (bug):
import traceback
...
logger.error(f"Campaign {pk} start error: {e}\n{traceback.format_exc()}")
logger.error(f"Campaign {pk} pause error: {e}\n{traceback.format_exc()}")
logger.error(f"Campaign {pk} resume error: {e}\n{traceback.format_exc()}")
logger.error(f"Campaign {pk} cancel error: {e}\n{traceback.format_exc()}")
```

O `{e}` coloca `str(e)` e o `{traceback.format_exc()}` coloca o traceback completo
no campo **message** do log record.

Campanhas de WhatsApp disparam chamadas à WhatsApp Business API, cujas exceções
de HTTP frequentemente incluem URLs com `access_token` em query params ou
tokens Bearer no corpo da resposta de erro. Isso coloca credenciais de API
nos logs como texto livre, ignorando qualquer scrubbing por campo configurado
em Sentry/CloudWatch/Datadog.

#### Correção

```python
# DEPOIS:
# import traceback removido
logger.exception("Campanha %s: erro ao iniciar", pk)
logger.exception("Campanha %s: erro ao pausar", pk)
logger.exception("Campanha %s: erro ao retomar", pk)
logger.exception("Campanha %s: erro ao cancelar", pk)
```

`logger.exception` registra o traceback em `exc_info` (campo separado),
onde redatores de campo do aggregator funcionam. O `import traceback` foi
removido pois não era usado em nenhum outro lugar no arquivo.
